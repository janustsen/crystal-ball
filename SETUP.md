# Run Crystal Ball

This checkout is an Expo React Native prototype. It runs anonymously, using local Ollama and optional local Supabase. No hosted credentials are included. Current verification uses Expo web390×844 because this Mac has Command Line Tools but no Xcode/iOS runtime. Native integrations are not claimed simulator-verified.

## Local development

1. `npm install` (Node22+).
2. Start Ollama with task-local models and a dedicated port: `OLLAMA_MODELS="$PWD/.local/models" OLLAMA_HOST=127.0.0.1:11435 OLLAMA_NO_CLOUD=1 ollama serve`. In another shell: `OLLAMA_HOST=127.0.0.1:11435 ollama pull qwen3:4b-instruct-2507-q4_K_M`.
3. Install Supabase CLI, then `supabase start` from this checkout. Project id crystal-ball-prototype uses55321API,55322Postgres,55323Studio. Docker is required. Anonymous auth is enabled; migrations install per-user row-level policies. `supabase status -o env` displays this local project's keys. Never use another project's key.
4. Copy `.env.example` to `.env.local`. Populate only EXPO_PUBLIC_SUPABASE_ANON_KEY from the local output. This public local anon key is not a service-role key. With Supabase configured the app is server-metered, so the engine shell also needs this local project's `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` (see below); without them the engine refuses signed-in readings. Cloud backup is opt-in; see [Apple backup setup](docs/launch/app-store.md#apple-backup-setup-and-release-blockers).
5. `npm run server`, then `npm run web -- --host lan`. Open http://localhost:8087 or this iMac’s private Tailscale URL http://janus-mac.tail8d2280.ts.net:8087. Leave EXPO_PUBLIC_ENGINE_URL unset for web: Metro forwards same-origin `/engine` requests to the loopback engine, including `/engine/social` and `/engine/health`. A native simulator still defaults to http://127.0.0.1:8787. The bridge is development-only; keep this preview on the trusted private network. `npm run web` generates/reuses a 256-bit secret in ignored `.local/preview-secret` (mode 0600) and injects it into the web client at startup. The page and JavaScript bundle load without a login prompt, as explicitly requested. The bundle includes the client token: it is a request guard, not user authentication or a secret from anyone who can reach this preview. Engine/social/health calls still require that token plus a same-origin Origin header; missing tokens and origin-less bridge calls are refused. Direct `expo start` without the injected token leaves engine calls closed. Keep access limited to the trusted private tailnet. Rotate by stopping the preview, deleting only `.local/preview-secret`, and restarting with `npm run web -- --host lan --clear` so Metro rebuilds the embedded key; existing clients must reload. Do not expose this development preview to the public internet. Story cards export locally as 1080×1920 PNG.
6. `npm run check && npm test`. Follow the [verification skill](.agents/skills/verify-crystal-ball/SKILL.md) for the current browser drives, remote bridge check and evidence requirements.

Local no-mistakes reviews also require `semgrep` and `gitleaks` on PATH, installed project dependencies, and an up-to-date `origin/main` ref with enough history to resolve its merge base with HEAD. See [the gate configuration](.no-mistakes.yaml) for the security checks and owner-disposition policy; `npm test` alone does not run these gates.

The server reads server-only variables from its shell, not Expo's public env loader. For live social features, export `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from this local Supabase project into the engine shell before starting it; copying them into `.env.local` alone does not configure the engine. Never prefix the service-role key with `EXPO_PUBLIC`. To exercise mock Plus and packs locally, also set `SOCIAL_MOCK_ENTITLEMENTS=true`; mock purchases then write the real local ledger, and this mode rejects non-loopback Supabase URLs. Leave it false for hosted use. Set the same `ENGINE_PORT` in both the engine and Metro shells when overriding the loopback engine port. Both fall back to `CRYSTAL_BALL_ENGINE_PORT` and then 8787; only the Node server additionally accepts `PORT` before 8787. Set server `APP_ORIGIN` to the preview origin when changing the preview port. Keep `EXPO_PUBLIC_ENGINE_URL` unset for the same-origin browser bridge. The committed default is MODEL_PROVIDER=ollama; no paid inference occurs by default. For the optional development-only Codex mode and hosted configuration, see [inference setup](docs/launch/hosted-model.md). Local addresses work in an iOS simulator; a physical phone needs a trusted LAN-accessible development server and matching EXPO_PUBLIC_ENGINE_URL/Supabase URLs. Do not expose the unauthenticated local Node adapter publicly.

School setup and the coarse-location App Store privacy note: [school boundary](docs/social/school.md). Apply the school migration after the social migration; its starter catalog covers three San Francisco schools. Name search is available on web and when location is denied.

## Room renders

The tabs sit in the approved AI-rendered library room. `node scripts/room-assets.mjs build <v2 render dir>` (ffmpeg on PATH) encodes it: the five spot stills and Home's loop are bundled under `assets/room/` (about 1.7 MB), `src/roomTrack.json` holds the per-frame ball track, and the 20 flights plus four other loops (about 15 MB, H.264) go to ignored `.local/room-assets/<version>/`. Those streamed clips are never committed. `node scripts/room-assets.mjs sync <destination>` rsyncs them to a local path or `host:path`.

If `.local/room-assets` is absent, `sync` first builds from `ROOM_RENDER_SOURCE`, defaulting to `/Users/janustsen/dev/archive/crystal-ball-room/v2`. The source directory must contain the approved `camera/`, `stills/`, `idle/`, and `flights/` renders; ffmpeg and rsync must be on PATH. Build outputs stay in this checkout.

For the complete component flight matrix, copy `scripts/room-preview.tsx` to `app/room-verification.tsx` before starting the preview, then add `ROOM_SCENE_URL=http://localhost:<preview-port>/room-verification` to the driver command below. This temporary route mounts the real room with five controls because the app hides tabs during Ask. Remove `app/room-verification.tsx` after testing; it must not ship.

For a local preview, run `node scripts/room-assets.mjs sync public/room` and start Expo with `EXPO_PUBLIC_ROOM_ASSET_BASE=/room`; Metro serves `public/` on the preview's own port. Then run `PREVIEW_URL=http://localhost:<preview-port> node scripts/drive-room.mjs` for app navigation, adding the harness setting above for all 20 ordered spot-pair flights and their landing loops. Without the asset-base variable, tab changes cut straight to the stills. The app prefetches the streamed clips after launch, keeps them in the Cache API on HTTPS or localhost origins (the HTTP cache elsewhere), and cuts to the still until a clip is loaded. The bundled Home loop loads separately without using the Cache API.

Production hosting is a later credential step: upload `.local/room-assets/` to a public CDN or Supabase Storage bucket keeping the `<version>/<clip>.mp4` layout, serve `video/mp4` with long-lived immutable caching and CORS for the web origin, and set `EXPO_PUBLIC_ROOM_ASSET_BASE` to its base URL. Before rebuilding changed renders, bump `roomVersion` in `scripts/room-assets.mjs`; the build writes that version into `src/roomTrack.json` and the streamed folder so old caches never mix with new clips. Native builds show the stills until follow-up `cb-native-room-video` adds expo-video playback.

## Known prototype boundaries

Remote HTTP origins cannot access browser speech recognition. The Ask flow offers typing when voice is unavailable; localhost or an HTTPS origin plus microphone permission is needed for real browser recording. Story export is a local 1080×1920 PNG. Supabase is optional for local history and memory; cloud mirroring and live social features require it. The [verification skill](.agents/skills/verify-crystal-ball/SKILL.md) documents the isolated social transport fallback and its limits.

Forecasts are speculative, never proven future knowledge. Sensitive requests soft-block; classification fail-closed errors consume no reading. English plus a few Spanish/Danish phrase patterns is not multilingual safety coverage. Social privacy and sample-star behavior are defined in the [social boundary](docs/social/model.md). The Apple backup panel is hidden on web and unavailable or unconfigured native builds. It appears only when iOS Apple authentication is available, Supabase is configured, and EXPO_PUBLIC_APPLE_LINK_ENABLED=true; web notification controls explain their native requirements. Friend links carry only the question and friend flag, not private answers. Approved anonymous Stars are visible to other app users through Tonight’s Sky. No App Store submission or automatic external posting is included; purchase modes and outstanding account setup follow the [billing guide](docs/launch/billing.md).

The preview's paywall is in labeled `mock` mode; EAS builds use real App Store purchases. See [billing](docs/launch/billing.md).

### Daily omen widget and check-ins

Home generates one personal astrology-flavored omen per local anonymous profile/day, using remembered facts and the current profile’s `sunSign`. `src/api.ts` maps that sign into the request-only `facts.sun_sign`, replacing any legacy remembered sign, and sends birthday/confirmation through the [API age gate](#reading-profile-and-birth-chart); profile changes do not reset the daily quota. The existing engine accepts `action: "omen"`; see [provider output caps](docs/launch/hosted-model.md#implemented-boundary). Local Ollama remains the default (no service spend). The shared provider keeps one constrained repair on invalid output, then fails closed. No reading credit is spent. One generation request is claimed durably before inference; failures remain unavailable for that day rather than retrying on each visit. This is the prototype's device-local quota, not a cross-device server quota. The daily generation claim survives Forget everything; see [README](README.md) for reset behavior and failure notices.

The iOS `DailyOmen` widget uses the `expo-widgets` config plugin in app.json; `npx expo prebuild --platform ios --no-install` generates its extension and app-group entitlement. A development build is required (not Expo Go). Open Home before adding the widget. It displays the same personal omen, then switches to “Open the Ball for today’s omen” at the next local midnight; the widget never triggers model calls. Web and Android show the omen on Home without a native widget.

Check-in scheduling uses a valid forecast `dueDate` (YYYY-MM-DD) at local noon, falling back to creation date plus 30 days when the date is absent or invalid. The engine produces ball-set `dueDate` values for new forecasts; retention consumes them without generating dates. See [README](README.md) for automatic scheduling, permission and outcome controls.

Device widget rendering and notification delivery/tap navigation remain unverified until Xcode setup is complete. Evidence and boundary limits are in `docs/evidence/retention-validation.md`. After creating a real reading in a named chrome-devtools-axi session, `scripts/drive-retention.sh` repeats the retention checks; its default session is `cb-retention` (override `CHROME_DEVTOOLS_AXI_SESSION` when needed).

For concurrent local verification, use the engine-port settings in [Local development](#local-development). Keep `EXPO_PUBLIC_ENGINE_URL` unset so browser calls retain the same-origin bridge.

## Reading profile and birth chart

The profile is local-first: optional `birthday` (ISO date), lowercase `sunSign`, `ageBand` (`teen`, `adult`, or null), and optional `birthTime`, `birthPlace`, `moonSign`, `risingSign`. `ageConfirmed`, `onboardingDone` and `onboardingBlocked` persist the [onboarding age gate](README.md). Newly confirmed skippers use `ageBand: teen`; forgetting an eligible profile’s birthday preserves its existing age band and confirmation. Reading safety still uses teen-safe rules whenever the birthday is absent. An unconfirmed profile cannot read or mirror to Supabase. Onboarding blocks under-13 birthdays before cloud identity creation. The plan/predict/omen/chart API requires a valid 13+ `viewerBirthday` or, when no birthday is supplied, `ageConfirmed: true`; it rejects ineligible requests before inference. Optional `personName` must pass the first-name validation in `src/profile.ts`; the engine also checks that the question names that person before model access. Output classification follows the [all-age safety policy](docs/research/safety-policy.md).

After [birthday editing or birth-detail removal](README.md), the mirror writes the scrubbed facts and reading payloads on the next state update, retrying after failures on a later change. Configured Supabase deletion has not been verified; `tests/profile-retention.test.ts` covers the payload and owner-scoped deletion boundaries.

Moon/rising use the pinned `circular-natal-horoscope-js` ephemeris on device. Its published `module` entry points at absent source, so Metro imports the shipped `dist/index` bundle. City lookup is a separate, no-key prototype boundary using [Open-Meteo / GeoNames](https://open-meteo.com/en/docs/geocoding-api); only the city query is sent. The hosted free endpoint is non-commercial: production needs a licensed or self-hosted lookup before activation. No paid account or credentials are configured.

The reading API and social friend action accept an optional `viewerChart` with valid lowercase `moonSign` and `risingSign`, accompanied by a valid `viewerBirthday`. `server/viewer-chart.ts` owns validation. With billing configured, the server checks the viewer’s Plus balance before including those signs in the saved astrology line; the viewer context is independent of the subject’s filtered facts. The local preview without billing accepts valid chart context without that entitlement check.

`action: "chart"` uses the same chart validation and sends only the month and three signs to the model. With billing configured, `server/billing.ts` uses the service-only claims in `supabase/migrations/202610060080_chart_weather.sql` to enforce Plus and the [monthly allowance](README.md). Without billing, the loopback preview generates directly without a server quota or entitlement check. The supplied local date must be within one day of the server's UTC date. The provider allows one repair, then fails closed; failed generation releases the claim for retry. The app stores successful text as `chartWeather: {month, text}` for the local calendar month; this is only a device cache. See [user controls](README.md) for credit usage and birth-detail changes, and `tests/plus-chart-voice.test.ts` for boundary coverage.

New forecasts include `dueDate` as `YYYY-MM-DD`; it is optional only for older saved forecasts. Personal-reading timeframe validation and client requests use the user’s local calendar day; Circle forecasts follow the [social date contract](docs/social/model.md#social-v2). The API validates the optional `localDate` before forecast generation; requests omitting it fall back to the server’s current date. `src/due-date.ts` owns whole-duration and current/future-date validation; `tests/local-calendar.test.ts` covers western and eastern timezone boundaries. See [check-in scheduling](#daily-omen-widget-and-check-ins) for retention behavior. `astrology` and the short `why` remain visible to free users; `deeperWhy` plus inputs/assumptions/sources are displayed to Plus users. Expanded explanation visibility remains client-side; reading charges and entitlements follow the [billing contract](docs/launch/billing.md).

## Social v2 delivery

Apply all migrations in `supabase/migrations` in filename order; `202610040050_billing.sql` replaces the earlier client charge-marker RPC. The [billing contract](docs/launch/billing.md) owns Circle charging. See the [social contract](docs/social/model.md#social-v2) for feature behavior. Run `bash scripts/verify-social-db.sh` for real PostgreSQL authorization, quota and single-claim checks.

Set `EXPO_PUBLIC_WEB_ORIGIN` to the deployed HTTPS web origin for sealed links, including native builds. Development web previews default to their current origin and may use HTTP; native previews must configure their reachable preview origin explicitly. Both new and redisplayed seals use this browser URL. Existing incoming seal routing still handles its query parameter; native universal-link association requires deployment configuration.

Set `EXPO_PUBLIC_INSTALL_URL` to the released app-store or install landing page so browser seal recipients get an install button. Without a release URL, the preview offers the `crystalball://` app link and an installation nudge. Browser recipients use an anonymous session and see no headline until they tap the ball.

After opening a seal (or failing to, for example when someone else already claimed it), a browser visitor can ask one free web reading through the normal Ask flow, then is sent to install. The engine limits it to one per browser, one per network (salted SHA-256 of the first `X-Forwarded-For` address) per UTC day, and a global daily cap, with a light SHA-256 proof-of-work bot check. No account or Supabase session is charged. Claims live in `web_readings` (`202610060060_web_readings.sql`, service role only); without Supabase the loopback engine keeps them in memory until restart. Server-only settings: `WEB_READING_DAILY_CAP` (default 500) and `WEB_READING_SALT` (defaults to the service-role key). `X-Forwarded-For` can be spoofed if the edge proxy passes client values through; the browser limit, proof and global cap still apply.

On web, one Make clip tap records a 1080×1920 video (MP4 where the browser's MediaRecorder supports it, otherwise WebM) of the reveal with the app's own chime and hum, then hands it to the share sheet or downloads it. Native clips need a view-to-video recorder module in a development build; until one is added, native users keep Replay for recording with the device screen recorder.

Circle and Sky pushes require an EAS project ID (`extra.eas.projectId`), configured APNs/FCM credentials, a native development/release build, and explicit in-app permission. Run `npx tsx scripts/open-sky.mts` hourly with the same Supabase variables and the model provider's server variables; it writes each School's and Circle's weekly [Friday Sky](docs/social/model.md#friday-sky) omen once, and accepts an ISO time to replay a missed week. Run `npx tsx scripts/deliver-social-pushes.mts` once per minute in a trusted scheduler with `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; set server-only `EXPO_ACCESS_TOKEN` if Expo enhanced push security is enabled. Never expose this worker as a public unauthenticated endpoint. It leases up to 100 due Circle jobs and 100 due Sky jobs per run. Circle claims recheck blocking/membership/revocation and send generic messages for seals, invites, joins, group forecasts and due votes. Sky delivery follows the separate [explicit opt-in and claim eligibility contract](docs/social/model.md#friday-sky); [README](README.md) describes its prompt and settings. It never sends questions, headlines, omens, activity or glow. Delivery is at least once after transient failures; an accepted Expo ticket is not proof of device delivery. One token per account is supported in this prototype; Circle and Sky pushes share it with separate consent flags. Native delivery, store installation and scheduler deployment need release-environment verification; no credentials or infrastructure are provisioned by the local test adapter.
