# Run Crystal Ball

This checkout is an Expo React Native prototype. It runs anonymously, using local Ollama and optional local Supabase. No hosted credentials are included. For recorded web and Simulator coverage, see [verification evidence](README.md), including the [native glass record](docs/evidence/native-glass-2026-10-09/README.md). For native setup and remaining device verification limits, see [Native development](#native-development).

## Local development

1. `npm install` (Node22+).
2. Start Ollama with task-local models and a dedicated port: `OLLAMA_MODELS="$PWD/.local/models" OLLAMA_HOST=127.0.0.1:11435 OLLAMA_NO_CLOUD=1 ollama serve`. In another shell: `OLLAMA_HOST=127.0.0.1:11435 ollama pull qwen3:4b-instruct-2507-q4_K_M`.
3. Install Supabase CLI, then `supabase start` from this checkout. Project id crystal-ball-prototype uses55321API,55322Postgres,55323Studio. Docker is required. Anonymous auth is enabled; migrations install per-user row-level policies. `supabase status -o env` displays this local project's keys. Never use another project's key.
4. Copy `.env.example` to `.env.local`. Populate only EXPO_PUBLIC_SUPABASE_ANON_KEY from the local output. This public local anon key is not a service-role key. With Supabase configured the app is server-metered, so the engine shell also needs this local project's `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` (see below); without them the engine refuses signed-in readings. Cloud backup is opt-in; see [Apple backup setup](docs/launch/app-store.md#apple-backup-setup-and-release-blockers).
5. `npm run server`, then `npm run web -- --host lan`. Open http://localhost:8087 or this iMac’s private Tailscale URL http://janus-mac.tail8d2280.ts.net:8087. The browser uses its same-origin `/engine` bridge, which Metro forwards to the loopback engine, including `/engine/social` and `/engine/health`. Native development defaults to `http://127.0.0.1:8787`. Set `EXPO_PUBLIC_ENGINE_URL` only to override these defaults. The bridge is development-only; keep this preview on the trusted private network. `npm run web` generates/reuses a 256-bit secret in ignored `.local/preview-secret` (mode 0600) and injects it into the web client at startup. The page and JavaScript bundle load without a login prompt, as explicitly requested. The bundle includes the client token: it is a request guard, not user authentication or a secret from anyone who can reach this preview. Engine/social/health calls still require that token plus a same-origin Origin header; missing tokens and origin-less bridge calls are refused. Direct `expo start` without the injected token leaves engine calls closed. Keep access limited to the trusted private tailnet. Rotate by stopping the preview, deleting only `.local/preview-secret`, and restarting with `npm run web -- --host lan --clear` so Metro rebuilds the embedded key; existing clients must reload. Do not expose this development preview to the public internet. Story cards export locally as 1080×1920 PNG.
6. `npm run check && npm test`. The dev-transport integration test creates and removes a disposable local PostgreSQL cluster; `initdb`, `pg_ctl`, and `psql` must be on PATH, or set `PG_BIN` to their PostgreSQL bin directory. Follow the [verification skill](.agents/skills/verify-crystal-ball/SKILL.md) for the current browser drives, remote bridge check and evidence requirements.

Local no-mistakes reviews also require `semgrep` and `gitleaks` on PATH, installed project dependencies, and an up-to-date `origin/main` ref with enough history to resolve its merge base with HEAD. See [the gate configuration](.no-mistakes.yaml) for the security checks and owner-disposition policy; `npm test` alone does not run these gates.

The server reads server-only variables from its shell, not Expo's public env loader. For live social features, export `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from this local Supabase project into the engine shell before starting it; copying them into `.env.local` alone does not configure the engine. Never prefix the service-role key with `EXPO_PUBLIC`. To exercise mock Plus and packs locally, also set `SOCIAL_MOCK_ENTITLEMENTS=true`; mock purchases then write the real local ledger, and this mode rejects non-loopback Supabase URLs. Leave it false for hosted use. Set the same `ENGINE_PORT` in both the engine and Metro shells when overriding the loopback engine port. Both fall back to `CRYSTAL_BALL_ENGINE_PORT` and then 8787; only the Node server additionally accepts `PORT` before 8787. Set server `APP_ORIGIN` to the preview origin when changing the preview port. The browser automatically uses the same-origin bridge. The committed default is MODEL_PROVIDER=ollama; no paid inference occurs by default. For the optional development-only Codex mode and hosted configuration, see [inference setup](docs/launch/hosted-model.md). For simulator and physical-phone connectivity, follow [Native development](#native-development). Do not expose the unauthenticated local Node adapter publicly.

School setup and the coarse-location App Store privacy note: [school boundary](docs/social/school.md). Apply the school migration after the social migration; its starter catalog covers three San Francisco schools. Name search is available on web and when location is denied.

## Room renders

The tabs sit in the approved AI-rendered library room. `node scripts/room-assets.mjs build <v2 render dir>` (ffmpeg on PATH) encodes it: the five spot stills, Home's loop and the 20 flights (`assets/room/flights/`, about 13 MB with the push-in, H.264) are bundled under `assets/room/`, so a tab change flies on web and native with no clip host; `src/roomTrack.json` holds the per-frame ball track, and the four other loops go to ignored `.local/room-assets/<version>/`. The same build adds the Plus art from the local-AI bake-off entry (`PLUS_RENDER_SOURCE` or a third argument, defaulting to `/Users/janustsen/dev/archive/crystal-ball-bakeoff/pipeline`): the Inner Library's resting still and its push-in (`flights/home-library.mp4`), both bundled, and per ball style a glass disc, its glint-free interior and a picker preview under `assets/styles/` (about 0.3 MB in all). The streamed loops are never committed. `node scripts/room-assets.mjs sync <destination>` rsyncs them to a local path or `host:path`.

If `.local/room-assets` is absent, `sync` first builds from `ROOM_RENDER_SOURCE`, defaulting to `/Users/janustsen/dev/archive/crystal-ball-room/v2`. The source directory must contain the approved `camera/`, `stills/`, `idle/`, and `flights/` renders; the Plus source must also be available for the build. ffmpeg and rsync must be on PATH. Build outputs stay in this checkout.

Do not edit `src/roomTrack.json` by hand.

For the complete component flight matrix, copy `scripts/room-preview.tsx` to `app/room-verification.tsx` before starting the preview, then add `ROOM_SCENE_URL=http://localhost:<preview-port>/room-verification` to the driver command below. This temporary route mounts the real room with five controls because the app hides tabs during Ask. Remove `app/room-verification.tsx` after testing; it must not ship.

Flights need no setup. For the other spots' loops in a local preview, run `node scripts/room-assets.mjs sync public/room` and start Expo with `EXPO_PUBLIC_ROOM_ASSET_BASE=/room`; Metro serves `public/` on the preview's own port. Then run `EXPO_PUBLIC_ROOM_ASSET_BASE=/room PREVIEW_URL=http://localhost:<preview-port> node scripts/drive-room.mjs` for app navigation, adding the harness setting above for all 20 ordered spot-pair flights and their landing loops. Without the asset-base variable, those spots rest on their stills. On web the app loads the bundled flights after launch (HTTP cache) and cuts to the still until a clip is loaded; streamed loops follow and stay in the Cache API on HTTPS or localhost origins (the HTTP cache elsewhere). Native plays the bundled flights with expo-video and has no loops.

Hosting the loops is a later credential step: upload `.local/room-assets/` to a public CDN or Supabase Storage bucket keeping the `<version>/<clip>.mp4` layout, serve `video/mp4` with long-lived immutable caching and CORS for the web origin, and set `EXPO_PUBLIC_ROOM_ASSET_BASE` to its base URL. Before rebuilding changed renders, bump `roomVersion` in `scripts/room-assets.mjs`; the build writes that version into `src/roomTrack.json` and the streamed folder so old caches never mix with new clips.

## Native development

With Xcode and an iOS Simulator runtime installed and the license accepted, run `npx expo run:ios`. Xcode 27 builds require the scene life cycle on iOS 27: the `plugins/scene-lifecycle.js` config plugin in `app.json` adopts `EXExpoAppSceneDelegate` during prebuild. Regenerate existing native projects with `npx expo prebuild --platform ios` before rebuilding this change. Use an Expo development build, not Expo Go, for speech recognition and purchase integrations. App scheme crystalball; bundle com.janustsen.crystalball. Verify VoiceOver, Dynamic Type200%, keyboard avoidance, safe-area, Android back, automatic listening, tap-to-stop and cleanup when leaving voice, the [dated check-in flow](README.md) and notification permission. These checks are separate from the browser pass.

For a physical phone using the private preview bridge, start the preview as above, then build with `EXPO_PUBLIC_ENGINE_URL` set to its reachable URL including `/engine` (for example, `http://janus-mac.tail8d2280.ts.net:8087/engine`) and `EXPO_PUBLIC_PREVIEW_SECRET` set to the value in that preview checkout’s `.local/preview-secret`. Native requests supply the engine URL’s origin alongside the token; browsers supply their own Origin header. Rebuild the native client after rotating the embedded token. When the engine has `SUPABASE_URL`, it meters every reading, so the phone build also needs `EXPO_PUBLIC_SUPABASE_URL` (phone-reachable) and `EXPO_PUBLIC_SUPABASE_ANON_KEY`; a build without them sends no session and every reading fails with “Open an anonymous session first.”

At **prebuild** time, `app.config.js` adds an iOS ATS insecure-HTTP exception for exactly the configured engine hostname only when the URL uses HTTP and the hostname ends in `.ts.net`; other URLs keep `app.json`’s local-networking policy. Export `EXPO_PUBLIC_ENGINE_URL` and `EXPO_PUBLIC_PREVIEW_SECRET` in the shell **before** running `npx expo prebuild --platform ios`, and keep that environment for Xcode bundling. Setting them only for `xcodebuild` updates JavaScript but leaves the generated native transport policy stale. `NSAllowsLocalNetworking` alone does not allow an HTTP `.ts.net` hostname. Regenerate and rebuild after changing that hostname.

Before installing a bundled Release build, run `python3 scripts/check-ios-engine.py /absolute/path/to/CrystalBall.app` in that same environment. It checks the built `Info.plist` and `main.jsbundle`, including the current preview token, without printing it. A successful `/engine/health` from curl does not check iOS transport policy.

## Known prototype boundaries

Remote HTTP origins cannot access browser speech recognition. The Ask flow offers typing when voice is unavailable; localhost or an HTTPS origin plus microphone permission is needed for real browser recording. Story export is a local 1080×1920 PNG. Supabase is optional for local history and memory; cloud mirroring and live social features require it. The [verification skill](.agents/skills/verify-crystal-ball/SKILL.md) documents the isolated social transport fallback and its limits.

Forecasts are speculative, never proven future knowledge. Sensitive requests soft-block; classification fail-closed errors consume no reading. English plus a few Spanish/Danish phrase patterns is not multilingual safety coverage. Social privacy and sample-star behavior are defined in the [social boundary](docs/social/model.md). The Apple backup panel is hidden on web and unavailable or unconfigured native builds. It appears only when iOS Apple authentication is available, Supabase is configured, and EXPO_PUBLIC_APPLE_LINK_ENABLED=true; notification platform limits follow [user guidance](README.md). Friend links carry only the question and friend flag, not private answers. Approved anonymous Stars are visible to other app users through Tonight’s Sky. No App Store submission or automatic external posting is included; purchase modes and outstanding account setup follow the [billing guide](docs/launch/billing.md).

The preview's paywall is in labeled `mock` mode; local Xcode Release builds use real App Store purchases (as do the optional EAS store profiles). See [billing](docs/launch/billing.md).

### Daily omen widget and check-ins

Real sky uses the installed `circular-natal-horoscope-js` ephemeris through `src/real-sky.ts`, at 20:00 on the requested calendar date in the viewer’s IANA time zone. Event boundaries are local midnights, including daylight-saving changes. Omen requests must supply `localDate` and `timeZone`. The event reading applies on a full Moon, new Moon or the day Mercury turns retrograde; event text must name the event, and the supplied Moon sign is allowed only as a Moon-position reference, not an invented personal sign. Validation collects violations for the shared single repair. Friday Sky’s shared time convention is owned by the [Friday Sky contract](docs/social/model.md#friday-sky).

Once the Daily insight is unlocked (see [usage](README.md)), Home generates one personal astrology-flavored omen per local anonymous profile/day, using remembered facts other than The Ball asks answers and the current profile’s `sunSign`. `src/api.ts` maps that sign into the request-only `facts.sun_sign`, replacing any legacy remembered sign, and sends birthday/confirmation through the [API age gate](#reading-profile-and-birth-chart); profile changes do not reset the daily quota. The existing engine accepts `action: "omen"`; see [provider output caps](docs/launch/hosted-model.md#implemented-boundary). Local Ollama remains the default (no service spend). The shared provider keeps one constrained repair on invalid output, then fails closed. No reading credit is spent. Each generation request is claimed durably before inference, with at most two a day: a failed or interrupted first request gets one retry on the next load (Home reloads every minute and on return), then the day stays unavailable. The same request returns Tonight’s whisper; the provider’s single repair covers both fields, so an unrepairable whisper fails the omen closed. This device-local quota is separate from the [hosted server limits](docs/launch/hosted-model.md#paid-and-user-controls). The daily generation claim survives Forget everything; see [README](README.md) for reset behavior and failure notices.

The iOS `DailyOmen` widget uses the `expo-widgets` config plugin in app.json; `npx expo prebuild --platform ios --no-install` generates its extension and app-group entitlement. A development build is required (not Expo Go). Open Home before adding the widget. It displays the same personal insight, then switches to “Open the Ball for today’s insight” at the next local midnight; the widget never triggers model calls. Web and Android show the insight on Home without a native widget.

Check-in date resolution uses a valid forecast `dueDate` (YYYY-MM-DD), falling back to creation date plus 30 days when the date is absent or invalid. `src/ritual.ts` owns local notification planning, and `src/notify.ts` is the shared scheduling and persisted daily-budget boundary; features register candidates rather than scheduling directly. The engine produces ball-set `dueDate` values for new forecasts; retention consumes them without generating dates. See [README](README.md) for automatic scheduling, permission and outcome controls.

Device widget rendering remains unverified. Earlier retention evidence is in `docs/evidence/retention-validation.md`; dated notification delivery and tap observations are in [engagement evidence](docs/evidence/engagement-2026-10-09/README.md), not a verification of subsequent scheduler changes. After creating a real reading in a named chrome-devtools-axi session, `scripts/drive-retention.sh` repeats the retention checks; its default session is `cb-retention` (override `CHROME_DEVTOOLS_AXI_SESSION` when needed).

For concurrent local verification, use the engine-port settings in [Local development](#local-development). Use the browser engine override documented there to retain the same-origin bridge.

## Reading profile and birth chart

The profile is local-first: optional `birthday` (ISO date), lowercase `sunSign`, `ageBand` (`teen`, `adult`, or null), and optional `birthTime`, `birthPlace`, `moonSign`, `risingSign`. `ageConfirmed`, `onboardingDone` and `onboardingBlocked` persist the [onboarding age gate](README.md). Newly confirmed skippers use `ageBand: teen`; forgetting an eligible profile’s birthday preserves its existing age band and confirmation. Reading safety still uses teen-safe rules whenever the birthday is absent. An unconfirmed profile cannot read or mirror to Supabase. Onboarding blocks under-13 birthdays before cloud identity creation. The plan/predict/bond/omen/chart/insight/year API requires a valid 13+ `viewerBirthday` or, when no birthday is supplied, `ageConfirmed: true`; it rejects ineligible requests before inference. For plan/predict, optional `personName` must pass the first-name validation in `src/profile.ts`; the engine also checks that the question names that person before model access. The bond action requires `personName` validated by `validFirstName` in `src/social-policy.ts` and generates its own shared question without a planning step. Output classification follows the [all-age safety policy](docs/research/safety-policy.md).

After [birthday editing or birth-detail removal](README.md), the mirror writes the scrubbed facts and reading payloads on the next state update, retrying after failures on a later change. Configured Supabase deletion has not been verified; `tests/profile-retention.test.ts` covers the payload and owner-scoped deletion boundaries.

Moon/rising use the pinned `circular-natal-horoscope-js` ephemeris on device. Its published `module` entry points at absent source, so Metro imports the shipped `dist/index` bundle. City lookup is a separate, no-key prototype boundary using [Open-Meteo / GeoNames](https://open-meteo.com/en/docs/geocoding-api); only the city query is sent. The hosted free endpoint is non-commercial: production needs a licensed or self-hosted lookup before activation. No paid account or credentials are configured.

The reading API and social friend action accept an optional `viewerChart` with valid lowercase `moonSign` and `risingSign`, accompanied by a valid `viewerBirthday`. `server/viewer-chart.ts` owns validation. With billing configured, the server checks the viewer’s Plus balance before including those signs in the saved astrology line; the viewer context is independent of the subject’s filtered facts. The local preview without billing accepts valid chart context without that entitlement check.

`action: "chart"` uses the same chart validation and sends only the month and three signs to the model. With billing configured, `server/billing.ts` uses the service-only claims in `supabase/migrations/202610060080_chart_weather.sql` to enforce Plus and the [monthly allowance](README.md). Without billing, the loopback preview generates directly without a server quota or entitlement check. The supplied local date must be within one day of the server's UTC date. The provider allows one repair, then fails closed; failed generation releases the claim for retry. The app stores successful text as `chartWeather: {month, text}` for the local calendar month; this is only a device cache. See [user controls](README.md) for credit usage and birth-detail changes, and `tests/plus-chart-voice.test.ts` for boundary coverage.

New forecasts include `dueDate` as `YYYY-MM-DD`; it is optional only for older saved forecasts. Personal-reading timeframe validation and client requests use the user’s local calendar day; Circle forecasts follow the [social date contract](docs/social/model.md#social-v2). For plan/predict requests, the API validates the optional `localDate` before forecast generation; requests omitting it fall back to the server’s current date. `src/due-date.ts` owns whole-duration and current/future-date validation; `tests/local-calendar.test.ts` covers western and eastern timezone boundaries. See [check-in scheduling](#daily-omen-widget-and-check-ins) for retention behavior. `astrology` and the short `why` remain visible to free users; `deeperWhy` plus inputs/assumptions/sources are displayed to Plus users. Expanded explanation visibility remains client-side; reading charges and entitlements follow the [billing contract](docs/launch/billing.md).

## Social v2 delivery

Apply all migrations in `supabase/migrations` in filename order; `202610040050_billing.sql` replaces the earlier client charge-marker RPC. The [billing contract](docs/launch/billing.md) owns Circle charging. See the [social contract](docs/social/model.md#social-v2) for feature behavior. Run `bash scripts/verify-social-db.sh` for real PostgreSQL authorization, quota and single-claim checks.

Set `EXPO_PUBLIC_WEB_ORIGIN` to the deployed HTTPS web origin for sealed links, friend links and Circle invitations, including native builds; its host is also the web address printed on story cards and the reveal clip’s end card. Web builds without it use their own page origin (including HTTP previews). Without a valid origin, story-card and reveal-clip exports refuse with “Configure the Crystal Ball web origin before sharing a link.” Native builds must configure it; Replay for recording displays the address when available. Both new and redisplayed seals use this browser URL. Existing incoming seal routing still handles its query parameter; native universal-link association requires deployment configuration.

Set `EXPO_PUBLIC_INSTALL_URL` to the released app-store or install landing page so browser seal recipients get an install button. Without a release URL, the preview offers the `crystalball://` app link and an installation nudge. Browser recipients use an anonymous session and see no headline until they tap the ball.

For the [sealed-link visitor flow](README.md) (and new browsers arriving by a friend or Circle link), the engine limits free web readings to one per browser, one per network (salted SHA-256 of the first `X-Forwarded-For` address) per UTC day, and a global daily cap, with a light SHA-256 proof-of-work bot check. No account or Supabase session is charged. Claims live in `web_readings` (`202610060061_web_readings.sql`, service role only); without Supabase the loopback engine keeps them in memory until restart. Pending claims temporarily count toward all three limits and expire after ten minutes; failed or blocked forecasts release them early when possible. Expired pending claims are removed on the next claim, so a failed release or timed-out claim does not consume the browser’s reading permanently. Successful forecasts mark claims completed before returning: completed browser claims remain consumed, while completed network claims and the global cap count only for their UTC day. Server-only settings: `WEB_READING_DAILY_CAP` (default 500) and `WEB_READING_SALT` (defaults to the service-role key). `X-Forwarded-For` can be spoofed if the edge proxy passes client values through; the browser limit, proof and global cap still apply.

See [recording usage and platform limits](README.md) for reveal clips. Native automatic recording requires a view-to-video recorder module and a development build.

Circle and Sky pushes use native APNs tokens, with no Expo account or EAS project ID. Supabase's `open-sky` Edge Function runs hourly; `social-push` runs minutely through pg_cron/pg_net and a Vault-backed scheduler secret. Apple APNs auth keys stay server-only. The worker preserves generic payloads, membership/block/consent checks, leased retries and one token per account. An APNs acceptance is not proof of display or tap routing. See the [launch infrastructure and exact settings](docs/launch/infrastructure.md) for deployment, credentials and release gates. Local `scripts/open-sky.mts` and `scripts/deliver-social-pushes.mts` remain manual development tools, not iMac production cron.

Without the paid Apple account, prove the server path in the iOS Simulator: build the app for a simulator (`npx expo prebuild -p ios`, then `xcodebuild` with `-sdk iphonesimulator CODE_SIGNING_ALLOWED=NO`), install it, allow notifications in the app, then run `npx tsx scripts/simulator-push.mts <simulator-udid> sky seal`. It runs the real delivery job and hands each message's APNs payload (`apnsPayload` in `server/social-push.ts`) to `xcrun simctl push` through an explicit Simulator sender; it always sends one fixture job per named kind and never connects to Supabase or claims real jobs, even when credentials are present. This proves payload, delivery to the app and tap routing, not APNs credentials or token registration, which still need Apple APNs keys and the paid account. The daily ritual's own notifications are local (`src/ritual.ts` plans them, `src/notify.ts` schedules them) and work on a free Personal Team install.
