# Social v2 boundary proof

The safety fact is that shared visibility is decided by PostgreSQL against the current viewer and membership, while published group questions/headlines require a service-written moderation receipt. Client snapshots cannot authorize discovery, voting, group publication, targeted delivery or membership growth.

`bash scripts/verify-social-db.sh` executes every committed migration in a disposable PostgreSQL cluster with Supabase-like permissive defaults, then uses separate anon/authenticated/service roles. The v2 proof checks adult/teen/unknown school discovery, the three-field search projection, both directions of blocking, silent declined requests, replay rejection, 5/10 memberships, owner transfer, content-free moments and glow, fixed emoji enforcement, direct receipt-write rejection, idempotent publication, one open forecast, due voting, leaving, targeted seal claims, service-only leased pushes and 20 pending requests/day. Existing tests also prove 20-member capacity, single-use link expiry and concurrent competing sealed claims. This is executed SQL/RLS proof, not hosted Auth/PostgREST verification.

The Reading boundary remains the existing device-local Store. Group publication uses the receipt UUID as its saved Reading ID, so retried publication and Store saving are idempotent; only the asker saves/debits it. The multi-person browser drive observes the asker's zero remaining daily Readings and the recipient's unchanged history and usage. Local balances and mock Plus remain prototype entitlements, not trusted billing.

Public Sky continues to rewrite and approve anonymous questions; Circle questions use a separate service-only receipt and member-only table. `tests/social-v2.test.ts` exercises the real handler with a deliberately refusing model and confirms that question and headline both use teen moderation before a receipt exists. The browser drive separately runs real Ollama; these prove gate wiring and sampled behavior, not comprehensive moderation or predictive accuracy.

Pushes use an enumerated outbox with no question or headline payload. The service claim filters current blocks, membership, seal revocation and pending invitations. Generic message dispatch and rejected-ticket retry behavior are tested with an explicit fake Expo transport. Native APNs/FCM delivery, EAS credentials, scheduler deployment and store installation remain unverified release prerequisites. Claims have a five-minute lease; delivery is at least once if a process fails after Expo accepts a ticket but before acknowledgment.

The new tables have RLS and remove default public/anon/authenticated grants. Definer functions pin an empty search path. Social push tokens are inaccessible directly to clients. The local verification adapter now understands the new RPCs and preserves optional SQL defaults; it remains loopback-only tooling.

Ownership transfer also changes a pre-existing school assumption. `circle_connections` preserves the accepted inviter/invitee pair instead of treating a new owner as everyone's inviter. The real SQL test transfers ownership among three same-school accounts and proves that existing co-members do not acquire a fabricated direct-invitation suggestion. Pending links/requests are invalidated when ownership changes. A two-process publication race proves that the Circle row lock permits exactly one future-due forecast.
